# Supabase production migration and verification checklist

This checklist applies to `sql/security_hardening.sql`. The migration changes PHI access boundaries, patient image storage behavior, and clinical audit logging. It must be reviewed by the institution’s Supabase administrator, clinical governance lead, and privacy/security owner before production execution.

## What the migration changes

| Area | Change |
|---|---|
| Unit access | Adds `unit_memberships`, adds `patients.unit_name`, and scopes patient records and child records to active unit members or administrators. |
| Patient images | Adds `storage_path`, makes the `patient-images` bucket private, and adds unit-aware object policies. |
| Signed access | The frontend stores a path and requests a one-hour signed URL. Public URLs are not generated by the updated image page. |
| Audit | Adds append-only `clinical_audit_events` for Emergency Mode dose calculations, Emergency Mode self-rechecks, and High-Risk Infusions same-doctor final re-checks. |
| Database helpers | Adds stable security-definer helper functions for unit membership, patient access, and safe patient UUID extraction from storage paths. |

## Required preflight

### Governance and access

1. Confirm the approved PICU unit names, doctor accounts, administrator accounts, patient-assignment model, and whether multiple units share the same Supabase project.
2. Decide whether the application should allow cross-unit emergency coverage. If it should, seed temporary active memberships rather than weakening RLS.
3. Confirm the retention period and access-review process for clinical audit events.
4. Confirm that the institution accepts the current audit payload: drug, weight, dose, concentration/rate where applicable, source metadata, actor, unit, optional patient UUID, and timestamp. No names or free-text notes are intended to be logged.
5. Schedule a maintenance window for image access changes and identify an owner for legacy image migration.

### Technical backup and staging

1. Confirm the Supabase project, branch, and database environment. Never apply this migration first to production.
2. Create a verified database backup and confirm that it can be restored or inspected before continuing.
3. Export or inventory the current `patients`, `patient_images`, `storage.objects`, `profiles`, and existing RLS policies. Preserve this inventory securely; it may contain PHI.
4. Apply the migration in a staging branch or isolated project with a representative schema and test accounts.
5. Record the migration commit SHA, Supabase project ref, operator, timestamp, and approval ticket.
6. Confirm that the deployed frontend version and the migration version are compatible. The signed-URL image page requires `patient_images.storage_path` and the private bucket policy.

## Staging execution order

Run the existing migrations first, if not already applied:

```text
sql/migration.sql
sql/subscriptions.sql
sql/security_hardening.sql
sql/teddy_bear_monographs.sql
sql/teddy_bear_monographs_seed.sql
```

Review the SQL in the Supabase SQL editor before execution. The hardening migration contains `DROP POLICY` statements for the old broad policy names and creates replacement policies. It is intentionally not a blind rollback script.

After the schema migration succeeds, apply `sql/teddy_bear_monographs.sql` and then run the authorized `sql/teddy_bear_monographs_seed.sql` file in the same private Supabase project. Verify that 238 rows are present and that every row has `review_status = 'pending-clinical-verification'` before opening the review route. Then seed approved unit memberships using a separately reviewed statement. Do not commit UUIDs to the repository:

```sql
INSERT INTO public.unit_memberships (user_id, unit_name)
VALUES
  ('approved-doctor-uuid', 'PICU');
```

For existing patients, assign and verify the unit before testing access:

```sql
UPDATE public.patients
SET unit_name = 'PICU'
WHERE unit_name IS NULL OR unit_name = '';
```

Use a controlled data-review process for any patient rows that belong to another unit. Do not use a broad update in production without a backup, approval, and row-count check.

## Signed image migration

The new private storage policy expects object paths in this format:

```text
patients/<patient-uuid>/<timestamp>_<filename>
```

Before production activation:

1. Set the `patient-images` bucket to private and verify its dashboard setting.
2. Inventory objects whose names do not match the expected patient path.
3. Map each legacy image row to its exact storage object and populate `patient_images.storage_path`.
4. Upload or move legacy objects into the patient-scoped path using a controlled server-side or administrator process.
5. Keep `storage_url` only as a migration reference until the institution approves removal. Do not expose legacy public URLs after the private cutover.
6. Verify that signed URLs expire and that a user from another unit cannot create or use a signed URL for the object.
7. Test upload, list, signed display, failed cross-unit access, and deletion with an approved doctor and a non-member test account.

The client creates signed URLs for one hour. Signed URLs are bearer links for their lifetime; do not put them in logs, analytics, screenshots, or permanent records.

## RLS verification queries

Run these checks with approved test accounts and record the results. Use a non-production test patient for negative tests.

```sql
-- Confirm the hardening objects exist.
SELECT to_regclass('public.unit_memberships'),
       to_regclass('public.clinical_audit_events');

-- Confirm RLS is enabled.
SELECT relname, relrowsecurity
FROM pg_class
WHERE relname IN ('unit_memberships', 'patients', 'fluid_balance',
                  'patient_drugs', 'investigations', 'patient_notes',
                  'patient_images', 'calc_results', 'clinical_audit_events');

-- Confirm private bucket status.
SELECT id, public
FROM storage.buckets
WHERE id = 'patient-images';

-- Review effective policies.
SELECT schemaname, tablename, policyname, cmd, qual, with_check
FROM pg_policies
WHERE tablename IN ('patients', 'patient_images', 'clinical_audit_events')
   OR tablename = 'objects'
ORDER BY tablename, policyname;
```

The negative access tests must confirm that an authenticated doctor who is not an active member of a patient’s unit cannot select, insert, update, or delete that patient’s rows, cannot list the patient’s image objects, cannot obtain a signed URL for them, and cannot read that patient’s audit events.

## Teddy Bear content verification

Run the following checks after the private monograph schema and seed are applied:

```sql
SELECT count(*) AS monograph_count,
       count(*) FILTER (WHERE review_status = 'pending-clinical-verification') AS pending_count,
       count(*) FILTER (WHERE content IS NULL OR length(content) = 0) AS empty_content_count
FROM public.teddy_bear_monographs;
```

The expected initial result is 238 rows, 238 pending rows, and zero empty-content rows. Confirm that the authenticated `/teddy-bear-review` route can search headings, open full content, save review metadata, and does not expose the table through a public route. Approval must not automatically modify Emergency Mode or Clinical Tools dose data.

## Audit-event verification

Use the application in staging and verify:

| Action | Expected event |
|---|---|
| Valid Emergency Mode dose calculation with an authenticated doctor | `emergency_dose_calculated` row with actor and unit |
| Emergency Mode “Acknowledge and verify result” action | `emergency_self_recheck` row |
| High-Risk Infusions final same-doctor re-check | `high_risk_infusion_self_recheck` row |
| Unauthenticated calculation | No insert; the UI still works as a reference aid without a server audit row |
| Invalid or non-UUID patient text | `patient_id` stored as `NULL`, not as arbitrary text |
| Free-text names, diagnoses, or notes inside metadata | Not stored because metadata is allowlisted |
| Wrong unit or non-member actor | Insert rejected by RLS |
| Direct event-type tampering | Rejected by the database check constraint |

Verify append-only behavior by confirming there are no client update or delete policies for `clinical_audit_events`. Review timestamps, actor IDs, unit names, and event counts without displaying unnecessary PHI.

## Production rollout

1. Freeze the migration commit and frontend commit being deployed.
2. Confirm the backup and approval records.
3. Apply the base and subscription migrations only if the production database does not already contain them.
4. Apply `sql/security_hardening.sql` during the approved maintenance window.
5. Seed and verify unit memberships using a secure SQL session.
6. Assign and verify all existing patients’ `unit_name` values.
7. Complete the private-image object/path migration before enabling image workflows for clinical use.
8. Run the RLS, signed-URL, and audit-event verification tests with approved positive and negative accounts.
9. Monitor Supabase logs, failed policy checks, signed-URL errors, image access errors, and audit insert failures.
10. Obtain clinical and security-owner signoff before declaring the migration complete.

## Rollback and incident handling

The hardening migration is not automatically reversible. Do not re-enable broad authenticated policies as an emergency shortcut without security-owner approval. If a critical issue occurs, first disable the affected UI workflow or revoke affected sessions while preserving the audit trail and evidence.

A rollback plan must be prepared in staging and approved before production. It should define how to restore database state, how to restore image object paths and bucket visibility, how to preserve audit records, and how to prevent unauthorized access during the transition. Any suspected PHI exposure should follow the institution’s incident-response and notification procedure.

## Definition of done

The migration is complete only when the institution has recorded: approved SQL and commit identifiers, successful backup verification, seeded unit memberships, verified patient-unit assignments, private bucket confirmation, successful positive and negative RLS tests, signed-URL expiry testing, audit-event constraint testing, monitoring ownership, clinical approval, and a rollback/incident plan.
